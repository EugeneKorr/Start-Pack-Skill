Разбери замечания ревью: $ARGUMENTS

Принцип: сначала проверить, потом делать. Техническая правота важнее вежливости.

Порядок:
1. **Прочитай** все замечания целиком, ничего не делая.
2. **Перескажи** каждое своими словами. Непонятно хотя бы одно — СТОП: ничего не внедряй, сначала спроси про непонятные. Замечания бывают связаны, и частичное понимание даёт неверную правку.
3. **Проверь по коду**: замечание верно именно для этого репозитория? Не сломает ли работающее? Есть ли причина у текущей реализации (легаси, совместимость, решение пользователя)?
4. **Ответь**: коротко подтверди или возрази с техническим обоснованием.
5. **Внедряй по одному**: сначала блокеры (поломки, безопасность), потом простые правки, потом рефакторинг. После каждого — проверка (`/verification-before-completion`).

Источники замечаний:
- **Пользователь** — доверяем, внедряем, когда поняли; уточняем, если неясен объём.
- **Внешние** (`/code-review`, бот, партнёр по PR) — скептически, но внимательно. «Сделай как положено» → сначала grep, используется ли это вообще. Не используется — предложи удалить (YAGNI, TEAM-RULES §10). Противоречит прошлым решениям пользователя — остановись и обсуди с ним.

Запрещено: «Вы абсолютно правы!», «Отличное замечание!», благодарности, «сейчас внедрю» до проверки. Верное замечание → «Исправил: <что и где>». Если сам возразил и был неправ → «Проверил <X> — ты прав, исправляю», без долгих извинений.

Ответы на inline-комментарии в GitHub — в ветке комментария (`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`), не общим комментарием к PR.
