# Агент «тикет → фикс»: ядро для всех проектов

_2026-10-23. Брейншторм с Владимиром. Идея — из разбора канала @ne_altman (Кирилл:
«тикет → классификатор → разработка»). Пересмотр того же дня: агент один на все проекты,
проектные источники — подключаемые модули (Владимир: «хочу агента под все проекты, а чтение
сообщений в СРМ — это доп модуль»). Пилот ядра — на Vega._

Модуль «сообщения клиентов в СРМ» — отдельный спек:
`EugeneKorr/crmvega` → `docs/specs/2026-10-23-ticket-to-fix-agent-pilot.md` (этап 2).

## Зачем

Баги по всем проектам приходят в чаты, от ботов-алертов и в issues. Владимир сам их
вылавливает, ищет репо и логи, воспроизводит, чинит с ИИ, отвечает людям. Цель — снять
вылавливание, первичный разбор и черновую работу, оставив ему ревью, выкатку и общение.

**Почасовая оплата.** В таймер идёт только время человека (постановка, ответы, проверка,
выкатка). Агент забирает неоплачиваемую часть; за час Владимир закрывает больше тикетов.
Работа агента без Владимира в таймер не идёт. Учёт часов в пилот не входит (решение 23.10).

## Было → станет

| Шаг | Было | Станет |
|---|---|---|
| Жалоба в рабочем чате проекта, от бота ошибок, в issues | Владимир читает и держит в голове | сборщик по расписанию заводит или дополняет issue в репо задач проекта |
| Дубли | Владимир склеивает сам | «ещё случай» комментарием в существующий issue |
| Какой репо чинить | Владимир помнит | реестр проекта: репо, их зоны, что трогать нельзя |
| Разбор, воспроизведение, фикс | Владимир + ИИ в живой сессии | фиксер ночью: падающий тест → фикс → проверки репо → draft PR |
| Запретные зоны (Bubble, бот СРМ, крупное) | вручную | issue + диагноз и план, без кода |
| Вопрос автору жалобы | Владимир пишет сам | черновик в сводке, отправляет Владимир |
| Сводка | нет | одна утренняя в «Избранное», разбита по проектам |
| Новый проект | — | файл в реестре + список модулей, ядро не меняется |
| Мерж и прод | Владимир | Владимир (без изменений) |

## Решения брейншторма

- Ядро — общее, живёт в Start-Pack-Skill; проектное — модулями и записями реестра.
- Автономия: до draft PR. Мерж, прод, деплой — только Владимир.
- Людям агент не пишет: только черновики. Отправка — только в «Избранное» Владимира.
- Метки в репо задач: `агент` + `агент:чиню` / `агент:разбор` / `агент:вопрос` / `агент:pr-готов`.
- Конвейер: сборщик (Sonnet) по расписанию + ночной фиксер (Opus), сводка утром.
- Запуск на Маке (launchd, Мак не засыпает), перенос на сервер — после пилота.
- Лимит фиксера на старт — 5 тикетов за ночь на все проекты, ~45 мин на тикет.
- Пилот ядра — Vega (три репо: СРМ, калькулятор, зеркало). Lleno, Parcelo — после пилота
  добавлением файла в реестр.
- Ключ OpenAI и замер по смыслу ядру не нужны (только модулю СРМ, и тот стартует на фразах).

## Термины

- **Ядро** — роли `collect` / `fix` / `digest`, наблюдатель, сторож, скрипты запуска.
  Ничего не знает о конкретных проектах.
- **Реестр** — `~/.claude/ticket-agent/projects/<проект>.json`, файл на проект.
- **Модуль-источник** — откуда брать находки. Общие модули работают в любом проекте с
  параметрами из реестра; проектные модули требуют чего-то в самом проекте.
- **Находка** — одна жалоба/алерт в общем формате: `{project, source, at, text, link, author}`.

## Модули-источники

| Модуль | Тип | Параметры | Что делает |
|---|---|---|---|
| `telegram-chat` | общий | `chat_id`, `name`, `kind` (`people` — жалобы людей, `alerts` — сообщения бота) | новые сообщения после курсора через Telegram MCP |
| `github-issues` | общий | `repo`, `labels`, `skip_authors` | новые открытые issues без метки `агент` |

## Роли ядра

**Сборщик** (Sonnet), 09:00, 14:00, 19:00 + по сигналу наблюдателя. По каждому включённому
проекту и каждому его источнику:

1. Новые находки после курсора (курсор — `state.json`, ключ `<проект>:<модуль>:<id источника>`).
2. Баг или нет. Не баг — строка в журнале.
3. Дубль — `gh search issues` в `issues_repo` → комментарий «ещё случай».
4. Какой репо: по `area` из реестра и тексту. Не понятно — `агент:вопрос`.
5. Сортировка: `агент:чиню` (один репо, одна зона, не в `forbidden_paths`, не из `fix_never`,
   мелкое по TEAM-RULES §1) / `агент:разбор` / `агент:вопрос`. В теле issue — строка
   «Репо: <key>».
6. Issue в `issues_repo` с метками проекта, репо, P0/P1/P2, `агент`, `агент:…`.

**Фиксер** (Opus), 03:00 + сразу по P0. Все проекты с `fix_enabled: true`, тикеты
`агент:чиню`, не больше 5 за ночь в сумме, P0 → P1 → P2. По тикету: worktree репо из строки
«Репо:» → падающий тест → фикс → `checks` репо → `/code-review` → draft PR в `slug` → метка
`агент:pr-готов`. Пересечение с открытым PR Владимира по файлам → пропуск. Две неудачные
проверки подряд → `агент:разбор` с описанием. Правило из `notes` репо — обязательная часть
проверки (например, смоук старта калькулятора).

**Сводка** (Sonnet), 07:30. Одно сообщение в «Избранное», блоки по проектам: 🔴 P0, ✅ PR
на ревью, 🔍 разборы, ❓ черновики вопросов, 🗑 «не баг», ⚠️ простои агента.

## Безопасность

- Безлюдный режим `claude -p` с отдельным `settings.json`: разрешено только перечисленное;
  мерж, push в main, деплой, `curl`, `supabase`, запись в БД, `gh api`, `gh label` — запрещены.
- Хук-сторож: `mcp__telegram__send_message` только с `chat_id = me`.
- `--add-dir` — все `path` из реестра и каталог worktree; рабочие деревья репо агент не меняет
  (только `git fetch` и `git worktree add`).
- В issues и сводке нет реквизитов клиентов: номера заявок и пересказ.

## Порядок включения

**Этап 1 — ядро на Vega, без единого изменения в проде:**
1. Ядро и модули `telegram-chat`, `github-issues` в Start-Pack-Skill (PR туда).
2. Реестр `vega.json`, метки в vova-workspace (по команде Владимира), launchd.
3. Сухой прогон сбора и сводки (`--dry`) → боевой сбор с `fix_enabled: false` неделю.
4. Включение фиксера (`fix_enabled: true`).

**Этап 2 — модуль `crm-client-chat`:** по своему спеку в crmvega (детектор на фразах v2,
утверждены 23.10; замер по смыслу не делаем), подключение — строкой `signals-table`
в `vega.json`.

**Дальше:** Lleno, Parcelo — файл в реестре, модули `telegram-chat` / `github-issues`.

## Оценка пилота (2 недели после включения фиксера)

Находки по источникам и проектам; сколько «не баг» ошибочно; судьба draft PR (как есть /
после правок / закрыт); время от жалобы до PR; ошибки выбора репо; расход лимита подписки;
время Владимира на ревью одного PR.

## Откат

`"enabled": false` в файле проекта — проект выпадает из всех ролей; `install-launchd.sh
uninstall` — агент выключен целиком. Issues и метки остаются.

## Self-review

1. **Персональные данные.** В issues и сводке только номер заявки и пересказ; длинные цифры
   маскируются. Модуль СРМ маскирует ещё при записи сигнала.
2. **Мак спит.** Сбор не идёт; курсоры подхватят пропущенное после пробуждения; сводка
   сообщает о простое. Срочное по СРМ (этап 2) приходит от самой Edge-функции.
3. **Безлюдный запуск.** Всё, чего нет в `allow`, не выполнится; проверка — сухой прогон.
4. **Ошибка выбора репо.** Сборщик пишет «Репо: …» с причиной; фиксер, увидев, что
   воспроизведение невозможно в этом репо, переводит тикет в `агент:разбор`. В оценке пилота —
   отдельная метрика.
5. **Несколько репо и worktree.** Каталог worktree общий, подкаталог `<проект>-<репо>-<issue>`.
6. **Проверки репо разные и тяжёлые** (`npm ci`, `uv pip install`). Укладываются в лимит
   ~45 мин; при нехватке — тикет в `разбор`, не сокращать проверки.
7. **Известные красные тесты** (`analyze-deal` в СРМ) — в `notes` репо, чтобы фиксер не
   принимал их за свою регрессию и не «чинил» по пути.
8. **Подсчёт часов.** Сессии агента названы «🤖 агент: …»; при ручном учёте отбрасывать.
9. **Нагрузка на Женю.** Агентные issues только с меткой `агент`; при > 15 за неделю — обсудить.
10. **Telegram-чат с людьми и алертами — один модуль.** `kind` подсказывает сборщику, как
    читать: у `alerts` один и тот же текст повторяется часто — склеивать по тексту ошибки.
